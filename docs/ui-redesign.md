# UI revision 1.2

The task/controller contracts remain authoritative and unchanged. This revision addresses the real Desktop journey: inline forms push the board away, a 340px detail column overflows, long analysis hides actions, the queue budget resets when returning from a Session, and cards show the assignment queue even after an actual claim.

## References

- [Dashi taskboard](https://github.com/chuspeeism/dashi-taskboard) `723c400e`: separate task editor/detail surfaces, property grouping, explicit dialog dismissal and task navigation.
- [sparkDash](https://github.com/MiaAI-Lab/sparkDash) `3e6d4ef6`: compact metric cards, subtle surface borders, 16px corners, restrained semantic accents, semantic state dots and readable secondary labels. The user's existing LAN deployment was visually inspected.
- DSH 0.2.1-rc.2: native slots, generated Remote, official color tokens and framework Session state. No host DOM or private state changes.

## Theme

The brand accent follows DSH `--dsw-alias-state-business-primary` (light `#4176e6`; dark inherits the active DSH theme, `#7aaaff` in 0.2.1-rc.2) and primary labels follow `--dsw-alias-label-primary-foreground`. This single token drives the primary button, keyboard focus ring, checkbox/radio, stat icons, card hover/selection, selected tab underline, audit nodes and attention surfaces. Dark mode and foreground colors therefore follow the enclosing DSH theme instead of plugin-owned orange literals.

Stage dots are semantic state colors, not brand accent. `needs-info #e1a44c` and `in-review #c5a052` intentionally keep warm amber, while success `#28ad79` and danger `#df5c67` keep their established meanings. Do not recolour them to blue merely because the primary accent changed.

## Components and navigation

- Bounded main canvas, metric cards, one workspace/filter toolbar, task board/list and Session table.
- An automation control card explicitly distinguishes current queue execution from watching new issues. Its budget follows the actual activation and cannot disable another workspace's queue.
- Task cards show actual claimed execution Session before assignment fallback, execution phase and criterion progress.
- New task and task detail are plugin-owned native HTML dialogs, modeled after Dashi's editor. Native top-layer modality supplies inert background and focus containment. Escape/backdrop/close share one dismissal path, restore invoking focus, and protect unsaved creation, property and evidence drafts with a nested confirmation. No new OS window is spawned.
- Detail tabs separate overview/criteria/evidence, analysis/review, completion rules/properties, and activity. Header and footer stay reachable; only the dialog body scrolls. No detail view changes the board width or its scroll position.
- Long evidence, identifiers and plan entries wrap inside bounded surfaces. Narrow dialogs fill the available viewport. Controls remain keyboard accessible; reduced motion is respected.


## Create-task information architecture

The create dialog is task-first and single-column. It asks for task details first, then execution arrangement, and keeps scheduling/completion details behind a collapsed "Advanced settings" disclosure. Dependencies and resource keys are optional scheduling constraints, not part of the task definition.

- Dependency candidates are limited to active, non-archived tasks in the same workspace; completed tasks are excluded because they are already satisfied. Selected dependencies render as removable chips and a search field appears when the list grows.
- The executor control defaults to the workspace queue and offers only execution-capable Sessions; analysis and review phase Sessions are filtered out and a busy execution Session is disabled.
- Resource keys use a type/value builder (file, port, build directory, database, branch, other) and store the existing `namespace:value` form. The raw fallback remains only for "other".
- The completion mode is a simple three-option selector in the execution section; instructions and machine checks stay in the advanced disclosure.
- "Analyze before execution" explains the criteria behaviour: empty criteria are generated by analysis, while owner-written criteria become acceptance expectations. Direct execution requires criteria.
